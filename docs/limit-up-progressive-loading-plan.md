# 短线连板分批加载优化方案

日期：2026-09-17。目标：开源版。状态：分批加载已实现并验证。前五节保留诊断和实施方案，第六节记录实际交付。

目标：页面各区域按自己的数据就绪时间显示；本地历史、基础梯队不等待题材补全和盘中行情。保留已有计算口径与数据来源优先级。

## 2. 当前阻塞链路

### 前端：请求并行，但渲染仍受全页条件限制

- `frontend/src/App.tsx` 的 `refreshLimitUpWorkspace` 已并行调用梯队和情绪接口，各自更新状态。
- `frontend/src/components/LimitUpWorkspace.tsx` 在没有梯队数据时提前返回全页 loading / error，位于后面的 `EmotionHistoryPanel` 无法显示。
- 所以单纯把请求改成并行不会解决问题，需要将各区域的加载与错误状态独立渲染。

### 梯队：只在所有补充信息完成后返回

`backend/internal/httpapi/limit_up_ladder.go` 的 `limitUpLadderCache.load`：

1. 梯队内存缓存有效期 30 秒。过期后同步重建，不先返回上次结果。
2. 并行请求 `RecentLimitUps(ctx, 8)` 和全市场 `StockCatalog`，但等待两者全部结束。
3. 构建今日、昨日梯队及题材归因。
4. 再调用实时行情，补齐昨日涨停股当前涨跌幅，然后整个接口才返回。

进一步追踪 provider：

- 开盘啦 `LimitUpPools` 持有服务刷新锁；过期时同时刷新涨停池和板块轮动，等待两者都完成才保存并返回。板块轮动自身还串行请求前 3 个题材的龙头。
- `duanxianxia.LimitUpProvider.RecentLimitUps` 在开盘啦读取之后再调用东方财富，即使开盘啦已经有数据也会同步等待补充完成。
- 东方财富 `RecentLimitUps(ctx, 8)` 从旧到新逐日串行请求 8 个自然日的涨停池，并非只读取展示所需的最近两个交易日。
- 全市场概念目录有 3 分钟缓存，过期后分页取数且持有目录锁；只需要少量股票的梯队也要等待整个目录。
- 昨日梯队虽然默认折叠，昨日股票实时涨跌幅仍在首屏请求中加载。这些行情也用于盘中情绪，因此应后台独立加载，不能简单推迟到展开昨日面板时才取。

### 情绪：历史读取与实时计算、历史补齐绑定

`backend/internal/httpapi/market_emotion.go`：

- 历史读取完成后，接口还要补充盘中情绪。盘中缓存为 10 分钟，失效时调用同一个 `limitUpSnapshots.load`，与梯队请求共享进行中的任务，所以两个接口经常同时返回。
- `marketEmotionEngine.load` 持有互斥锁执行历史读取和可能的外部同步。后台 scheduler 同样调用它，页面可能等待正在执行的同步任务。
- 历史缺失或需要更新时，同步过程包含 24 个自然日涨停池、概念目录、炸板与跌停池，以及昨日股票逐股日 K；首次最多构建 7 个交易日。
- 历史接口设置 150 秒 context 超时，scheduler 设置 4 分钟；普通互斥锁的等待也不能靠请求取消及时退出。已有 SQLite 历史不能因此被同步任务挡住。

## 3. 数据如何分批显示

以下是依赖关系，不规定固定展示顺序，也不添加人为延时。

| 页面区域 | 首批可用内容 | 后续补充 | 必须等待 |
| --- | --- | --- | --- |
| 页面框架 | 标题、筛选、局部占位 | 状态和更新时间 | 无 |
| 历史情绪时间轴 | SQLite 已有日快照 | 新交易日与缺失历史 | 仅本地读取 |
| 今日摘要、连板梯队 | 上次快照或先到的涨停池 | 缺失股票、金额等行情字段 | 一份有效涨停池 |
| 昨日梯队、晋级率 | 留存的对应交易日涨停池 | 缺失历史补齐 | 相匹配的今日、昨日结构 |
| 炒作题材热度 | 缓存归因或可用的开盘啦题材 | 龙头归属、目录辅助归因 | 自己的题材依据 |
| 盘中情绪、昨日股当前涨幅 | 上次有效结果并标注时间 | 实时行情和覆盖率计算 | 基础梯队与必要行情 |

K 线和龙虎榜已按用户点击加载，不在此次首屏关键路径。龙虎榜同日列表复用可作为后续独立优化。

## 4. 建议分三批实施

### 第一批：解除页面与情绪历史的等待

- 页面始终显示框架；梯队、情绪历史、盘中情绪分别处理 loading / error / refresh。
- 将历史的本地读取与外部同步分开，GET 先返回 SQLite 结果；过期或缺失历史在后台去重同步。读取已有结果不获取覆盖远程请求的引擎锁。
- 盘中情绪独立更新，不让历史时间轴等 `limitUpSnapshots.load`。可以增加独立盘中接口，保留原接口默认行为用于兼容。
- 无历史时显示“历史初始化中”，后台结束后再取结果；同步失败进入可重试状态，不无限显示初始化。
- 页面刷新保留已有数据；切页、切换后端配置、再次刷新时取消旧请求并校验请求代次，防止旧响应覆盖新数据。

这一批可释放 4 ms 已返回的历史，也可在梯队慢达十余秒时展示本地历史，但仍需第二批缩短梯队本身的首批等待。

### 第二批：梯队分阶段发布，缓存优先

- 参考趋势题材的实现，为梯队增加 `delivery=progressive`；保留默认完整响应的兼容行为。
- 先返回内存或持久化的上次有效梯队，标明交易日期、源数据更新时间、是否过期。无缓存则返回模块状态并启动一次后台任务。
- 开盘啦增加只读涨停池缓存入口；现有 `CachedSnapshot` 仅覆盖题材快照，不能直接当涨停池使用。
- 刷新服务允许涨停池、题材快照各自完成后发布，避免涨停池等待题材龙头请求。保留刷新去重与上游频率约束，不能通过每次轮询重复触发外部请求。
- 当日涨停结构先发布；东方财富的历史及缺失字段补充、概念目录、昨日股实时行情各自更新对应区域。
- 昨日数据优先用留存交易日缓存；东方财富仅对未缓存或需刷新的日期取数，以有限并发补齐。首屏优先最近日期，不能机械取“日历昨天”替代上一交易日。
- 全市场概念目录优先用已有缓存；后台更新后再计算依赖目录的题材归因。维护原有开盘啦优先与东方财富补全语义。
- 后台任务采用服务生命周期 context 加独立总预算，不由第一个浏览器请求的取消终止全部订阅者的刷新。
- 各批次发布不可变快照；前端通过 `refresh_id`、版本号读取增量结果，轮询只读已有进度。完成、失败、超时均进入终态。

### 第三批：计时、回归和交互细节

- 添加阶段耗时：本地缓存读取、刷新锁等待、涨停池、题材龙头、东方财富逐日补齐、概念目录、实时行情、情绪历史同步、首批发布与完整发布。
- 记录前端框架出现、首个有效区域出现、基础梯队出现和完整数据就绪的时间。
- 为刷新设置明确预算与退避；旧缓存可继续显示但不能伪装成刚更新的行情。
- 首屏方案稳定后，再优化龙虎榜同日列表缓存和个股弹窗请求取消。

## 5. 一致性与验收

- 未返回的统计、涨跌幅、题材热度显示待补充，不能用 0 或“无数据”代替未知。
- 每个模块携带交易日期、来源、源数据时间及刷新状态；不同交易日的今日、昨日、盘中反馈不能混算。
- 跨交易日保留历史快照供参考，同时明确标记日期；晋级率只在所需交易日数据齐全时发布。交易日选择以实际数据和交易日历为准。
- 单个补充源失败只影响对应区域；已成功的梯队和历史继续可见，明确展示行情覆盖不足。
- 有缓存的再次进入、重启后的持久化恢复、无任何缓存首次打开分别验证，不能用暖缓存结果代表全部场景。
- 可控回归至少覆盖：梯队延迟 10 秒而历史先到；历史同步慢而梯队先到；题材或实时行情延迟不阻塞基础梯队；上游失败保留旧数据；跨日不混算；重复刷新与离页不被旧响应覆盖；多个请求共享一次后台刷新；任务超时后停止轮询。
- 有可用本地缓存时，以 300 ms 内返回可用数据、500 ms 内显示首个有效区域作为初始验收目标，需在本机同条件测量确认。无缓存时按首个有效上游完成时间发布，不承诺外部网络耗时。

## 6. 实际实现与验证

### 已实现的行为

- 梯队与情绪历史接口增加 `delivery=progressive`；原完整响应模式保持兼容。
- 页面框架、摘要、历史情绪、梯队、晋级率、题材热度分别渲染。首次未知统计显示占位，刷新时保留已显示内容；盘中情绪无需等待历史初始化。
- 历史接口直接读取 SQLite，外部历史补齐由后台任务去重完成；与 scheduler 共享可取消等待的进行中任务，GET 不等远程同步锁。
- 梯队首次请求立即返回已有完整快照；后台先读取留存涨停池，再按开盘啦、东方财富逐日历史、题材、概念目录和行情的实际返回顺序发布内容。快照持久化到行情库，重启可恢复。
- 盘中情绪在梯队的行情阶段发布，不再由前端历史请求重复加载同一梯队。保留同交易日的上一份情绪结果并标注过期，行情就绪后替换。
- 开盘啦涨停池取得后立即保存和通知订阅者，不等待题材龙头；共享原有 5 分钟刷新限制，刷新锁等待支持取消。
- 东方财富历史按日期缓存、合并进行中请求；短线连板的渐进接口最多 3 个并发，最近日期优先，逐日发布结果。其他调用保留原有串行历史读取行为。当前日缓存 30 秒，已有非空历史日缓存 6 小时，错误短暂缓存 5 秒；部分历史失败明确报告，不用缺失日期计算晋级。
- 只使用与当前涨停池交易日相符的实时行情；较旧批次不能覆盖已恢复的较新交易日快照。行情补充使用独立副本，避免修改已发布对象。
- 前端单次只发一个轮询请求，从 250 ms 逐渐退避到 1.5 秒。刷新 ID 轮询只读；离页或重新刷新取消旧请求，忽略迟到响应；兼容桌面后端尚未重启时返回的旧版完整响应。梯队后台预算 25 秒、前端 35 秒；历史后台 150 秒、前端 160 秒。超时和局部失败均进入终态，保留可用结果。
- 新增各来源完成、逐日取数、首批发布、完整发布与本地历史读取的耗时日志。

### 验证结果

- 后端相关包普通测试通过：`httpapi`、`duanxianxia`、`eastmoney`、`sector`。
- 本次影响的梯队、情绪、缓存、分批加载与 provider 测试通过 race 检查。
- 前端 24 个测试文件、134 项测试全部通过，生产构建通过；构建仍有原有的大 chunk 提示。
- 浏览器控制延迟/失败回归通过：历史先于梯队显示、未知数字占位、基础梯队先于补充结果、盘中情绪先于历史初始化、局部失败不清空内容、刷新失败保留数据、切页后迟到响应不覆盖新页面。已检查局部加载与失败截图。
- 最终相关包普通测试、本次影响范围的 race 均通过；两项个股研究回归也单独通过 race 检查。并发历史取数已限定于渐进接口，原有消费者保留串行读取语义。没有将此前发生超时的全范围 race 运行计为通过。

### 真实上游抽样

用桌面行情库、情绪库的副本启动隔离后端；不读取模型凭据，不替换已有桌面进程。首次进程启动已有留存涨停池及 32 天情绪历史，尚无新增的梯队完整快照缓存。后台取数使用真实行情源。

| 测量项 | 单次观察 |
| --- | ---: |
| 情绪历史首次 HTTP 响应，含已有 32 天数据 | 43 ms |
| 梯队初始进度响应 | < 1 ms |
| 梯队首批可用数据被轮询读到 | 103 ms |
| 梯队所有阶段完成，均成功 | 3,330 ms |
| 重启后首次响应恢复完整梯队快照 | 10 ms |

后端日志显示留存梯队在 45 ms 发布；103 ms 包含验证程序约 100 ms 的轮询间隔，正式页面首次轮询间隔为 250 ms。上述为接口与数据就绪时间，不是浏览器完整绘制时间，也不是无缓存首次安装场景的性能承诺。与旧日志的 12.52 秒处于不同缓存和网络条件，不能当作严格同条件速度比。

原始测量、截图和回归记录保存在本地 `.runtime/limit-up-progressive-ui/`，不纳入开源提交。已安装桌面应用仍需后续构建/重启才会使用新后端。
